# Описание компонентной диаграммы системы «Vacancy Aggregator»

## 1. Обзор

Компонентная диаграмма отображает архитектуру веб-приложения «Vacancy Aggregator» — агрегатора вакансий с интеграцией HeadHunter. Система построена на основе **многослойной архитектуры** (Layered Architecture) с чётким разделением ответственности между слоями.

---

## 2. Описание компонентов системы

### 2.1. Presentation Layer — Frontend (Next.js 14, App Router)

**Назначение:** Пользовательский интерфейс приложения, обеспечивающий взаимодействие конечных пользователей с системой.

**Обоснование выбора Next.js 14 (App Router):**
- Server-Side Rendering (SSR) и Static Site Generation (SSG) для SEO-оптимизации страниц вакансий
- App Router обеспечивает серверные компоненты (React Server Components), снижая объём JavaScript на клиенте
- Parallel Routes для одновременного отображения списка и детальной страницы вакансии
- Встроенная маршрутизация на основе файловой системы

**Подкомпоненты:**

| Компонент | Описание |
|-----------|----------|
| **Страницы (App Router)** | Главная (`/`), Вакансии (`/vacancies`), Профиль (`/profile`), Админ-панель (`/admin`). Каждая страница — серверный компонент с возможностью SSR-префетчинга данных |
| **Features (FSD)** | Изолированные функциональные модули по методологии Feature-Sliced Design: `VacancyCard`, `FilterMenu`, `AuthBlock`, `EditProfile`. Обеспечивают высокую переиспользуемость и слабую связанность |
| **Widgets** | Составные компоненты, объединяющие features: `Search`, `VacancyList`, `TopBar`, `ProfileWidgets`. Представляют законченные секции интерфейса |
| **Shared UI Kit** | Библиотека базовых UI-компонентов: `Button`, `Badge`, `Select`, `SearchInput`, `Popup`, `Combobox`, `Checkbox`. Обеспечивает единый визуальный стиль |
| **Управление состоянием** | `TanStack React Query` — серверное состояние и кэширование; `React Hook Form + Zod` — формы с валидацией; `nuqs` — синхронизация фильтров с URL |

---

### 2.2. API Layer — tRPC v11

**Назначение:** Типобезопасный слой взаимодействия между клиентом и сервером, заменяющий традиционный REST API.

**Обоснование выбора tRPC:**
- End-to-end типизация — изменение серверной процедуры мгновенно отражается в клиентском коде без кодогенерации
- Нативная интеграция с TanStack React Query для кэширования и оптимистичных обновлений
- Поддержка middleware для сквозной авторизации
- Минимальный boilerplate по сравнению с REST/GraphQL

**Маршрутизаторы:**

| Router | Процедуры | Уровень доступа |
|--------|-----------|-----------------|
| `vacancy` | `createVacancy`, `updateVacancy`, `deleteVacancy`, `getVacancyItem`, `infinityVacancy` | CRUD — компания; чтение — публичное |
| `currency` | `getAllCurrencies` | Публичный |
| `vacancySync` | `getProfessionalRoles`, `syncFromHH`, `getImportRuns` | Только администратор |

**Middleware авторизации:**

| Процедура | Назначение |
|-----------|------------|
| `publicProcedure` | Доступна без авторизации |
| `protectedProcedure` | Требует авторизованного пользователя |
| `adminProcedure` | Требует роли ADMIN |
| `companyProcedure` | Требует роли COMPANY |

---

### 2.3. Authentication — NextAuth.js 4 (JWT)

**Назначение:** Аутентификация и авторизация пользователей, управление сессиями и ролевой моделью.

**Обоснование выбора NextAuth.js:**
- Нативная интеграция с Next.js (API Routes, middleware)
- Поддержка JWT-сессий без необходимости серверного хранилища сессий
- Расширяемая система провайдеров аутентификации
- Встроенная защита от CSRF

**Подкомпоненты:**

| Компонент | Описание |
|-----------|----------|
| **Credentials Provider** | Аутентификация по email/password с хешированием через bcrypt |
| **Session Management** | JWT-токены для stateless-сессий; токены содержат роль и ID пользователя |
| **Ролевая модель** | 4 роли: `ADMIN` (управление системой, синхронизация), `USER` (поиск вакансий), `GUEST` (ограниченный доступ), `COMPANY` (публикация вакансий) |

---

### 2.4. Business Logic — Сервисный слой

**Назначение:** Инкапсуляция бизнес-логики приложения, независимой от транспорта (tRPC) и хранилища (Prisma).

**Обоснование выделения в отдельный слой:**
- Разделение ответственности — бизнес-правила не зависят от API-фреймворка
- Тестируемость — сервисы можно тестировать в изоляции
- Расширяемость — добавление новых провайдеров вакансий не затрагивает API-слой

**Подкомпоненты:**

| Компонент | Описание |
|-----------|----------|
| **VacancySyncService** | Оркестратор синхронизации вакансий из внешних источников. Управляет процессом импорта: пагинация, маппинг данных, upsert в БД, ведение журнала импортов (`ImportRun`) |
| **HHProvider** | Адаптер для HeadHunter API (`api.hh.ru`). Реализует контракт внешнего провайдера вакансий. Выполняет HTTP-запросы с rate-limiting (300 мс между страницами) и User-Agent идентификацией |
| **ensureAdminExists** | Утилита инициализации — создаёт учётную запись администратора из переменных окружения при первом запуске |

---

### 2.5. Data Layer — Prisma ORM 6.6

**Назначение:** Абстракция доступа к данным, маппинг объектов приложения на реляционную модель БД.

**Обоснование выбора Prisma:**
- Декларативная схема данных с автоматическими миграциями
- Типобезопасный клиент — все запросы проверяются на этапе компиляции
- Prisma Studio для визуальной работы с данными при разработке
- Поддержка connection pooling

**Ключевые модели:**

| Модель | Описание |
|--------|----------|
| `Vacancy` | Вакансия — заголовок, описание, зарплата (от/до), компания, платформа, локация |
| `Platform` | Источник вакансии — локальная публикация или внешний импорт (hh) |
| `Currency` | Справочник валют для зарплатных данных |
| `Location` | Географическое расположение вакансии |
| `Users` | Учётные записи пользователей с ролями |
| `CompanyProfile / ClientProfile` | Профили компаний и соискателей |
| `ImportRun` | Журнал запусков синхронизации — статус, количество импортированных записей, ошибки |

---

### 2.6. Database — PostgreSQL

**Назначение:** Реляционное хранилище данных приложения.

**Обоснование выбора PostgreSQL:**
- Надёжная ACID-совместимая СУБД с широкой экосистемой
- Полнотекстовый поиск для вакансий
- Поддержка JSON-полей для хранения гибких структур (описания вакансий)
- Отличная совместимость с Prisma ORM

---

### 2.7. External Systems — Внешние системы

**Назначение:** Интеграция с внешними источниками данных для обогащения базы вакансий.

| Система | Описание |
|---------|----------|
| **HeadHunter API (hh.ru)** | Основной внешний источник вакансий. Используются эндпоинты `/vacancies` (поиск и получение вакансий) и `/professional_roles` (справочник профессиональных ролей). Интеграция без авторизации (публичное API) |
| **REST API (опциональный)** | Зарезервированный HTTP-клиент (Axios) для потенциальных дополнительных интеграций |

### 2.8. Infrastructure — Инструменты и стилизация

**Назначение:** Инфраструктурные инструменты, обеспечивающие качество кода, визуальную согласованность и тестирование.

## 3. Связи между компонентами

| Связь | Описание |
|-------|----------|
| Frontend → API Layer | tRPC Client через React Query; типобезопасные вызовы процедур |
| API Layer → Authentication | Middleware авторизации проверяет JWT-токен и роль перед выполнением процедуры |
| API Layer → Data Layer | Прямые запросы к Prisma Client для CRUD-операций над вакансиями и справочниками |
| API Layer → Business Logic | Делегирование сложной логики (синхронизация) в сервисный слой |
| Business Logic → External | HTTP-запросы к HeadHunter API через адаптер HHProvider |
| Business Logic → Data Layer | Массовый upsert вакансий и запись журнала импортов |
| Authentication → Data Layer | Чтение/запись пользователей, сессий, попыток входа |
| Data Layer → Database | Prisma Client генерирует SQL-запросы к PostgreSQL |

---

## 4. Архитектурные принципы

1. **Layered Architecture** — чёткое разделение на слои с однонаправленными зависимостями (сверху вниз)
2. **Feature-Sliced Design** — организация фронтенд-кода по функциональным срезам
3. **End-to-end Type Safety** — сквозная типизация от БД (Prisma) через API (tRPC) до UI (TypeScript)
4. **Adapter Pattern** — внешние системы подключаются через адаптеры (HHProvider), что упрощает добавление новых источников
5. **Separation of Concerns** — бизнес-логика вынесена в сервисный слой, независимый от транспорта и хранилища
